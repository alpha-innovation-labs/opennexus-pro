# Nexus marketing, business, and strategy plan

## Source policy

This plan only uses capabilities verified in repository files or official competitor sources. It does not invent product features. Proposed commercial packaging, pricing, and go-to-market moves are labeled as business decisions, not existing product capabilities.

## Current product facts from the repo

### Product identity

- Nexus is a custom Pi TUI app that bundles local extensions and uses `.nexus/` for project config. Source: `README.md`.
- The root package is private and versioned `0.2.19`; Pi config names the app `nexus` and config dir `.nexus`. Source: `package.json`.
- Release builds compile a Bun-powered native binary bundle and install only runtime assets still needed by compiled mode. Source: `README.md`, `scripts/release/buildBinaryBundle.mjs`.
- The npm release package generated by the repo is named `opennexus` and exposes `nexus` and `opennexus` binaries. Source: `scripts/release/npm-package/createReleaseNpmPackage.mjs`.
- Release safety is a non-negotiable constraint: shipped releases must not expose source code. The repo has e2e coverage proving the installed package has no `src` or `dist` trees. Sources: `AGENTS.md`, `test/e2e/release-executable/releaseNpmPackageDoesNotShipAppSource.test.ts`.

### Production-enabled features

The production compiled extension set is defined by `src/feature-flags/generated/compiledFeatureFlags.ts` and `src/extensions/generated/registerCompiledEnabledExtensions.ts`.

- Visual web annotation: `/annotate`, an annotate tool, and Chrome extension bridge.
- cmux integration: sync session titles to cmux pane titles and notify cmux tabs when panes finish. Runtime availability depends on `cmux` being available. Source: `src/feature-flags/applySystemExtensionAvailability.ts`.
- Context-window usage tool: `context_usage` for current chat context use.
- Exit summary: prints session title on app exit.
- FFF integration: FFF-backed read override, grep override, and `@` file autocomplete.
- Kanban modal: `/extension`, two-pane task board modal, temporary in-loop and completed task data.
- Markdown line editor: `/editor`, `demo.md` Markdown line modal, hidden persistent per-line chats, live reload with diff acceptance, Tron-styled right-panel mini chat.
- Neo editor: release flag is enabled; deeper repo docs describe custom promptline, slashusage, `@` autocomplete, editor trigger submit, and macOS `ctrl+v` image paste fallback. Sources: compiled flags and `.agents/skills/nexus/extensions/neo-editor.md`.
- Notifications: desktop notification on agent completion, default macOS submarine sound, `NEXUS_NOTIFY_SOUND_CMD` override.
- Observations: observation tracking, status widget, `/observations` command.
- RTK: bash rewrite and RTK-native read/find/ls/grep tools with fallback when `rtk` is unavailable. Source: `.agents/skills/nexus/extensions/rtk.md`.
- Startup logo: N logo on fresh startup.
- Sub-agent status widget: custom subagent working widget, live agent status lines, replaces Pi default loader.
- Sub-agents: RPC child-process subagent execution, custom context providers, background result lookup, and steering.
- Terminal modal: persistent shell, `/term` commands, terminal shortcuts.
- Tron UI: compact tool lines, thinking style, tool calls browser, user message bubble.

### Development-only or beta features not in the production compiled bundle

These should not be marketed as generally available until promoted into the release bundle.

- Playground: playground modal, `ctrl+i` shortcut.
- Todo: todo modal, `ctrl+\` shortcut.
- Workflows: `/workflow` command, Librarian and Engineer prompts, continuous subagent steering instructions.
- Workspace: session switcher, `ctrl+;` shortcut, workspace top bar.

Source: `src/feature-flags/generated/compiledFeatureFlags.ts`, where these are disabled in production and grouped as beta.

### External-channel status

- The gateway supports `nexus social-chat <start|stop|restart|status>`. Source: `apps/tui/src/cli/gateway/createGatewayUsageText.ts`.
- Telegram polling is enabled when `TELEGRAM_BOT_TOKEN` and `TELEGRAM_ALLOWED_USER_IDS` are present. Source: `README.md`.
- Built-in adapters are Telegram and Discord; Telegram is active polling, Discord is planned. Source: `.agents/skills/nexus/adapters.md`.

## Competitor review from official sources

### Claude Code

Official positioning: “agentic coding tool that reads your codebase, edits files, runs commands, and integrates with your development tools,” available in terminal, IDE, desktop app, and browser. Source: Anthropic Claude Code overview, `https://docs.anthropic.com/en/docs/claude-code/overview`.

What they are doing:

- Broad surface area across terminal, IDE, desktop, and browser.
- Positioning around codebase understanding, file edits, command execution, and development-tool integration.
- Clear official docs as the primary adoption channel.

Implication for Nexus:

- Nexus should not compete by claiming a wider surface. It should compete on a sharper terminal-native workflow: bundled extensions, sub-agent orchestration, browser annotation, persistent terminal, and release-safe binary packaging.

### OpenAI Codex CLI

Official positioning: “Codex CLI is a coding agent from OpenAI that runs locally on your computer.” Installation is via `npm i -g @openai/codex`, Homebrew cask, or GitHub release binary. It also points users to IDE and desktop app options. Source: OpenAI Codex README, `https://github.com/openai/codex`.

What they are doing:

- Simple install story across npm, Homebrew, and release binaries.
- Local-machine positioning.
- Uses existing ChatGPT plans for access, reducing purchase friction.
- Differentiates terminal, IDE, desktop, and cloud experiences.

Implication for Nexus:

- Nexus needs a one-command install and an onboarding path that demonstrates production-enabled features quickly. The current release package already supports binary-first npm distribution; commercial packaging should build on that.

### Gemini CLI

Official positioning: open-source AI agent that brings Gemini directly into the terminal, with terminal-first and Apache 2.0 open-source positioning. Install paths include `npx`, npm, Homebrew, MacPorts, and Anaconda. Source: Google Gemini CLI README, `https://github.com/google-gemini/gemini-cli`.

What they are doing:

- Open-source trust and broad package-manager availability.
- Terminal-first messaging.
- Low-friction no-install trial through `npx`.

Implication for Nexus:

- Nexus cannot copy the open-source distribution model because source exposure is explicitly prohibited for releases. It can copy the low-friction binary trial motion and use transparent docs, demos, and release tests to build trust without shipping source.

### Aider

Official positioning: “AI Pair Programming in Your Terminal.” It pairs with LLMs to start a new project or build on an existing codebase, maps the codebase, supports many languages, and can be used from an IDE/editor. Source: Aider README, `https://github.com/Aider-AI/aider`.

What they are doing:

- Memorable single-line category claim.
- Strong terminal-native identity.
- Codebase map as a trust-building feature for larger projects.
- Multi-model and editor-adjacent workflows.

Implication for Nexus:

- Nexus needs a concise category claim. Recommended: “the terminal AI workbench for agentic engineering teams.” This is proposed positioning, not a current feature claim.

### Cursor

Official positioning: “Built to make you extraordinarily productive, Cursor is the best way to build software with AI.” The public homepage also references agents that work in the terminal, collaborate in Slack, and review PRs in GitHub. Source: Cursor homepage, `https://www.cursor.com/`.

What they are doing:

- Outcome-led marketing, not feature-led marketing.
- Strong product-led growth through an AI editor.
- Multi-channel agent workflow narrative.

Implication for Nexus:

- Nexus should lead with measurable workflow outcomes: less context switching, terminal-native coordination, and faster review of agent activity. Do not lead with Pi internals or extension architecture.

### Goose

Official positioning: a native open-source AI agent with desktop app, CLI, and API for code, workflows, and automation. It also documents custom distributions with preconfigured providers, extensions, and branding. Source: Goose README, `https://github.com/block/goose` and moved project notice to AAIF.

What they are doing:

- Multi-surface product: desktop, CLI, API.
- General-purpose automation beyond code.
- Custom-distribution story for branded/packaged agent setups.

Implication for Nexus:

- Nexus has a natural business angle around a curated, branded, binary-only distribution with bundled extensions and controlled feature flags. That is closer to a commercial workbench than an open extension playground.

## Strategic positioning

### Category

Proposed category: terminal AI workbench for agentic engineering teams.

### One-line promise

Proposed promise: Nexus helps terminal-native developers run, steer, inspect, and coordinate AI coding agents from one polished binary.

### Differentiation grounded in current product

- Binary-first Nexus distribution with release tests preventing app source exposure.
- Bundled extension suite controlled by feature flags rather than user-installed extension sprawl.
- Sub-agent orchestration with status widgets, background result lookup, and steering.
- Developer UX improvements: Neo promptline, slashusage, file autocomplete, compact tool rendering, tool-call browser, and persistent terminal modal.
- Web-to-terminal bridge through visual Chrome annotation.
- External adapter foundation with Telegram active and Discord planned.

### What not to claim yet

- Do not claim enterprise SSO, hosted team dashboards, billing, cloud sync, Slack integration, PR review automation, Discord production support, or workspace/workflow/todo availability in production. These are not verified as production-enabled current features.

## Ideal customer profile

### Primary ICP

Small engineering teams and solo senior developers who already live in the terminal, use AI coding agents daily, and need better orchestration, visibility, and workflow polish than a basic chat CLI.

### Secondary ICP

Agencies and internal platform teams that want a controlled, branded AI terminal tool with bundled workflows and binary-only distribution.

### Excluded ICP for now

Large regulated enterprises requiring SSO, centralized admin, audit exports, or managed cloud controls. The repo does not show those capabilities today.

## Packaging and monetization plan

This is a proposed business model, not an existing product fact.

### Package 1: Nexus Individual

- Audience: solo developers and contractors.
- Includes: production binary, all production-enabled local features, email/community support.
- Pricing proposal: low monthly subscription or annual license.
- Sales motion: self-serve install and paywall after trial.

### Package 2: Nexus Team

- Audience: teams of 3–50 engineers.
- Includes: Individual features, team onboarding, private release channel, priority bug fixes, setup support for approved adapters such as Telegram.
- Pricing proposal: per-seat subscription.
- Sales motion: founder-led sales plus product-led trial.

### Package 3: Nexus Custom Distribution

- Audience: agencies, platform teams, and AI consultancies.
- Includes: branded binary, curated feature flags, custom defaults, adapter setup, training, and support SLA.
- Pricing proposal: annual contract plus implementation fee.
- Sales motion: direct sales.

### Package 4: Services revenue

- Implementation packages for local AI-agent workflow setup.
- Team training for agent orchestration and safe terminal workflows.
- Custom extension development, only when it does not compromise binary-only release constraints.

## Go-to-market plan

### Messaging pillars

1. Agent orchestration: sub-agents, status widgets, background lookup, steering.
2. Terminal workflow polish: custom promptline, `@` files, slash menu, persistent terminal, compact tool lines.
3. Web-aware coding: Chrome annotation bridge for UI debugging and review.
4. Controlled distribution: bundled extensions, feature flags, and binary-only release packaging.

### Proof assets to produce first

- 90-second terminal demo: launch Nexus, use `@` autocomplete, run a coding request, open tool-call browser, open terminal modal.
- Web debugging demo: use Chrome annotate, pass selected DOM/CSS context into the agent.
- Sub-agent demo: launch a sub-agent, show live status widget, retrieve background result, steer it.
- Release-trust page: explain binary-only packaging and cite no-source e2e tests without exposing private code.

### Launch sequence

#### Phase 1: Private founder-led alpha

- Target 10–20 terminal-heavy developers.
- Install through the existing binary release path.
- Success criteria: users complete first useful agent task, use at least two Nexus-specific features, and report one workflow they would miss if Nexus were removed.

#### Phase 2: Public waitlist and demo launch

- Publish landing page with the one-line promise, screenshots/GIFs, and private alpha call-to-action.
- Post demo clips to developer channels where terminal AI agent users already compare tools.
- Offer concierge onboarding for teams.

#### Phase 3: Paid beta

- Convert alpha users into paid Individual or Team plans.
- Keep production feature scope limited to compiled-enabled capabilities.
- Publish a public changelog for binary releases, not source.

#### Phase 4: Custom distribution sales

- Sell to teams that want a branded, curated terminal agent with controlled extensions.
- Use Goose’s custom-distribution positioning as category validation while differentiating on Nexus’s binary-only and bundled-extension approach.

## Sales strategy

### Wedge offer

“Install Nexus and we will help your team turn one repeated coding workflow into a faster agent-assisted terminal workflow in one onboarding session.”

### Discovery questions

- Which agent CLI or AI editor do your developers use today?
- Where do agents fail for you: context, visibility, steering, terminal handoff, browser/UI debugging, or team workflow consistency?
- What cannot leave local machines?
- Do you need a controlled binary distribution rather than open source?

### Demo path

1. Start with a real repo.
2. Show Neo promptline, slashusage, slash command discovery, and `@` autocomplete.
3. Launch a task that uses tools.
4. Show Tron compact tool lines and `/toolcalls`.
5. Open `/term` to inspect or run commands without leaving Nexus.
6. Use `/annotate` on a UI issue when relevant.
7. Run a sub-agent and show status/steering.

## Competitive strategy

### Against Claude Code and Codex CLI

Do not claim model superiority. Position Nexus as the workflow layer: a curated terminal workbench with sub-agent orchestration, browser annotation, and stronger in-terminal visibility.

### Against Gemini CLI and Aider

Do not compete on open source. Compete on bundled UX, release-controlled distribution, and team-ready packaging.

### Against Cursor

Do not compete as an editor replacement. Position Nexus as the terminal-native complement for developers whose core workflow remains shell, tmux/cmux, git, and CLI tools.

### Against Goose

Do not compete as a general-purpose desktop/API automation platform. Compete as a focused engineering TUI with curated extensions and binary-only commercial delivery.

## Product strategy constraints

### Keep production messaging aligned to compiled features

Production marketing must match `src/feature-flags/generated/compiledFeatureFlags.ts` and `src/extensions/generated/registerCompiledEnabledExtensions.ts`.

### Treat beta features as roadmap only

Workspace, workflows, todo, and playground are not production-enabled in the compiled release. Use them only in private demos clearly labeled beta.

### Protect source in every distribution channel

Every monetization plan must preserve the existing binary-only release discipline. Do not publish app source, source maps, dist trees, or repo internals in release artifacts.

## Metrics

### Activation

- Binary install completes.
- User starts a Nexus session.
- User invokes at least one production Nexus-specific feature.
- User completes one code task in a real repo.

### Engagement

- Sessions per active user per week.
- Use of `@` autocomplete, `/term`, `/annotate`, `/toolcalls`, and sub-agent flows.
- Repeat usage within seven days.

### Revenue

- Trial-to-paid conversion.
- Team pilot-to-contract conversion.
- Average revenue per team.
- Support hours per paid account.

## Risks and mitigations

### Risk: crowded market

Mitigation: avoid generic “AI coding agent” positioning. Lead with terminal workbench, orchestration, and bundled UX.

### Risk: source exposure

Mitigation: keep release tests mandatory and market only binary packages. Do not ship `src`, `dist`, source maps, or private repo artifacts.

### Risk: unverified beta claims

Mitigation: maintain a marketing source-of-truth generated from compiled feature flags before every release.

### Risk: model-provider dependency

Mitigation: position Nexus as workflow infrastructure rather than a model provider.

## Immediate CEO decision

Focus the first commercial wedge on teams that already use terminal AI coding agents and feel pain around visibility, steering, and context switching. Sell Nexus as the binary-only terminal AI workbench that makes agentic coding workflows easier to run, inspect, and control.
